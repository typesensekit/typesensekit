## Fixed locally

### 1. MCP strips field definitions before execution — high impact

`packages/mcp/src/server.ts` reconstructed the operation input from its Zod shape. That discarded the original object's passthrough behavior, stripping `type`, `facet`, and other field properties. A valid `collections.fields.add` MCP call failed with a missing-type error while the corresponding CLI operation accepted it.

The server now registers the original schema. Field lifecycle inputs also explicitly advertise `type`. A protocol regression test checks that a field's type and facet setting reach the HTTP request.

### 2. Timed-out work bypasses the concurrency limit — high impact

`packages/mcp/src/execution.ts` decremented active work when the timeout won `Promise.race`, although the Typesense request continued. Repeated timeouts could admit more work than the configured maximum.

A concurrency slot now remains occupied until the underlying task settles. The regression test times out one request, verifies another is rejected, then verifies capacity returns after the first finishes. Timeouts still do not cancel Typesense writes; the security guide now explains this.

### 3. Schema updates can drop fields without confirmation — high impact

`collections.update` accepts `{ fields: [{ name: "title", drop: true }] }`, but the shared destructive-operation classifier did not recognize that payload. This bypassed the CLI confirmation required by the dedicated field-drop command and advertised misleading MCP safety metadata.

The classifier now checks the fields in schema-update inputs and conservatively marks the operation destructive when generating metadata without an input. Adding a field alone remains non-destructive.

### 4. Malformed Host headers can cause an uncaught HTTP error — high impact

`packages/mcp/src/http-server.ts` constructed a URL using the incoming Host header before entering its error handler. A value such as `[` causes URL parsing to throw in the async request listener, potentially terminating Node through an unhandled rejection before authentication.

Routing now uses a fixed base, catches malformed request URLs, and has a regression test for an invalid Host value.

### 5. Failed Keychain saves expose the API key — high impact

`packages/cli/src/profile/credentials.ts` allowed `execFile` errors to propagate. Those errors include the complete `security ... -w <key>` command. A simulated failing executable confirmed that the CLI printed a fake credential.

The save path now throws a credential-free error without retaining the original error as its cause. A regression test covers the failure. The macOS command still receives the key as a process argument; this change specifically fixes error-output leakage.

## Remaining work, in priority order

### A. Refresh and validate dependencies

`pnpm audit --prod` reports **32 advisories: 1 critical, 15 high, 15 moderate, 1 low**. This includes website/build dependencies as well as package runtime dependencies; it is not evidence of 32 exploitable application vulnerabilities. The current CI workflow runs this command before `pnpm check`, so it would fail despite the historical green runs.

The critical [Astro advisory](https://github.com/advisories/GHSA-26w7-cxv4-gfx2) affects processing attacker-controlled AVIF images and is patched in Astro 7.2.8. The site builds static pages and uses ordinary image tags with repository assets; this audit did not identify that attack path in the deployed site. Other flagged packages include Hono, fast-uri, ip-address, qs, PostCSS, sharp, js-yaml, nanoid, svgo, and smol-toml.

Recommended next change: refresh compatible versions and the lockfile, reassess remaining advisories against actual use, run the complete checks and package dry runs, and test the Docker image. Keep dependency changes separately reviewable from the behavior fixes.

### B. Make API-key creation usable without weakening default redaction

`packages/core/src/operations/keys.ts` creates keys, but `packages/core/src/redaction.ts` deliberately redacts the returned `value` in both CLI and MCP output. A caller cannot obtain a newly generated key through the current interfaces. The existing test explicitly expects this redaction.

Design an explicit CLI-only secret retrieval/output option, or clearly document key creation as unsupported for retrieving generated credentials. Preserve default redaction and avoid exposing secrets to agents automatically.

### C. Validate examples and publish complete input schemas

`packages/cli/src/operation-docs.ts` generates an invalid `keys.create --examples` payload: it puts `description`, `actions`, and `collections` at the top level, while the operation requires a `value` wrapper. The current tests only check that every operation prints a command, not that the payload validates.

The custom schema serializer also emits `type: "unknown"` and omits validation constraints such as numeric bounds and string requirements. That output is not a complete JSON Schema contract. Add validation of every emitted example, curated lifecycle examples, and a supported Zod-to-JSON-Schema conversion.

### D. Apply limits to resource reads and bound batch fan-out

`packages/mcp/src/resources.ts` calls operations directly and serializes results outside the tool execution controller. Document/schema resource reads bypass its timeout, rate, concurrency, and response-size limits. This limitation is now explicit in the security guide.

Separately, `documents.get_many` starts one HTTP request per supplied ID with unbounded `Promise.all`. One admitted MCP call can therefore create many concurrent downstream requests. Bound both batch size and downstream concurrency; verify resource limits through protocol tests.

### E. Fix import automation failure handling

The automation example in `apps/web/src/pages/guides/typesense-cli-import-export-debugging.astro` pipes CLI output through `jq` and checks for failed rows. Without pipeline failure handling, a failed CLI invocation can leave an empty file and the row-count check can succeed.

Use an explicitly documented shell with `set -euo pipefail`, or capture and check the CLI exit status before parsing its output. Include a failure-path example or test.

### F. Review profile credential identity

Keychain entries use only the profile name as their account identifier. Two separate `--config` files containing the same profile name share a Keychain entry; saving one can change the credentials used by the other. Renaming a profile preserves the old Keychain reference, so reusing that old name can also affect the renamed profile.

Use a stable, unique credential reference per stored profile, with a migration plan for existing name-based references.
